# Simple Team Project Guidelines

**Project:** Smartphone Audio Sleep-Stage Model Development  
**Team:** Five researchers  
**Purpose:** Day-to-day rules for organizing work, collaborating, and recording results  
**Detailed reference:** [PROJECT_HANDBOOK.md](./PROJECT_HANDBOOK.md)  
**Technical strategy:** [MODEL_DEVELOPMENT_STRATEGY.md](./MODEL_DEVELOPMENT_STRATEGY.md)

This is the team's short operating guide. It does not prescribe experiment steps, model architectures, or research methods. The researchers will select those together through discussion and record important decisions in the project logs.

If this guide conflicts with the detailed handbook, follow the detailed handbook.

## 1. Directory Organization

Use the following basic structure:

```text
project/
├── README.md
├── TEAM_PROJECT_GUIDELINES.md
├── PROJECT_HANDBOOK.md
├── MODEL_DEVELOPMENT_STRATEGY.md
├── TEAM.md
│
├── configs/                         # Shared and release configurations
├── data/
│   ├── README.md                    # Data sources, rights and access instructions
│   ├── manifests/                   # Recording metadata; no raw audio
│   └── splits/                      # Frozen train/validation/test membership
├── eval/                            # Shared splits, metrics and evaluation runner
├── common/                          # Reviewed code reusable by the whole team
├── integration/                     # Teacher, student, hybrid and mobile candidates
│
├── researchers/
│   ├── r01/
│   │   ├── WORKPLAN.md
│   │   ├── STATUS.md
│   │   ├── src/
│   │   └── experiments/
│   ├── r02/
│   ├── r03/
│   ├── r04/
│   └── r05/
│
├── registry/
│   ├── EXPERIMENTS.md               # Master experiment index
│   ├── DECISIONS.md                 # Team decisions and rationale
│   ├── TEST_ACCESS.md               # Locked-test access history
│   └── RELEASES.md                  # Teacher freezes and student releases
└── reports/
    ├── weekly/
    ├── stage1/
    ├── stage2/
    └── final/
```

### Directory rules

- Each researcher develops inside `researchers/rXX/`.
- Shared, reviewed components go in `common/`.
- Only stage-gate and release candidates go in `integration/`.
- Canonical evaluation code belongs only in `eval/`.
- Large files such as audio, checkpoints, cached logits, and mobile builds stay in approved external storage. Commit only their manifests and hashes.
- Raw audio, personal identifiers, secrets, and access credentials must never be committed.

## 2. Project-Wide Rules

1. **Use one evaluation system.** Comparable metrics must be generated by the shared evaluator.
2. **Use the official data splits.** Do not create private train, validation, or test splits for comparable experiments.
3. **Prevent subject leakage.** All epochs and channels from the same participant and recording night remain in one split.
4. **Keep the test set locked.** Use validation for research decisions. Test access is allowed only for an approved checkpoint and must be logged.
5. **Discuss methods as a team.** Experiment priorities and technical methods are selected through team discussion, not permanently assigned by this guide.
6. **Record decisions.** Any choice that affects multiple researchers goes in `registry/DECISIONS.md`.
7. **Check existing work.** Search completed, running, and planned experiments before starting a new one.
8. **Keep work reproducible.** Every result must identify its code revision, complete configuration, data/split version, evaluation version, seed, and artifacts.
9. **Log every outcome.** Positive, negative, failed, stopped, and invalid experiments are all useful project knowledge.
10. **Protect shared code.** Changes to data definitions, splits, metrics, or integration code require review.
11. **Do not claim results from one lucky run.** Screening may use one seed, but conclusions and release decisions require repeated runs under the detailed handbook.
12. **Protect privacy and data rights.** Use only approved datasets and never transmit or expose raw bedroom audio outside the approved boundary.

## 3. Personal Researcher Rules

Each researcher must:

- use their assigned ID (`r01`-`r05`) in paths, experiment IDs, branches, and reports;
- keep `WORKPLAN.md` current with their agreed focus and planned experiments;
- work primarily within their own researcher directory;
- request review before changing `data/`, `eval/`, `common/`, or `integration/`;
- write model and data logic as reusable modules rather than notebook-only or monolithic scripts;
- keep configurations complete and avoid hardcoded local paths;
- run a small technical check before spending substantial compute;
- stop and report suspected data leakage, metric errors, privacy problems, or corrupted artifacts;
- update `STATUS.md` at least twice per week and after an important result;
- help reproduce at least one important result owned by another researcher;
- document blockers early instead of silently working around shared problems; and
- cleanly hand off reusable code, configurations, artifacts, and known limitations.

Researchers may collaborate across personal directories. One person remains the named owner of each experiment and is responsible for its records.

## 4. Experiment Records

### 4.1 Experiment ID

Use:

```text
s<stage>-r<researcher>-e<number>-<short-name>
```

Example:

```text
s1-r03-e012-noise-augmentation
s2-r02-e007-student-compression
```

### 4.2 Experiment folder

```text
researchers/rXX/experiments/<experiment-id>/
├── experiment.md          # Purpose and agreed plan
├── config.yaml            # Complete configuration
├── environment.json       # Software and hardware information
├── results.json           # Generated by the shared evaluator
├── notes.md               # Observations and conclusion
└── artifacts.json         # Artifact paths, versions and hashes
```

### 4.3 Minimum pre-run record

Before a substantial run, record:

- experiment ID and owner;
- status and project stage;
- hypothesis or question;
- parent/baseline experiment;
- related completed or planned work;
- what will change and what will remain fixed;
- metric or evidence used to make the decision; and
- expected compute and important risks.

The technical method is chosen by the team and described in the experiment record, not dictated by this guide.

### 4.4 Experiment status

Use one of these values:

| Status | Meaning |
|---|---|
| `PROPOSED` | Agreed and registered, not started |
| `RUNNING` | Currently in progress |
| `COMPLETE` | Evaluation and conclusion recorded |
| `FAILED` | Technical failure recorded |
| `STOPPED` | Intentionally ended early |
| `INVALID` | Result cannot support a claim |
| `SUPERSEDED` | Replaced but retained in history |

## 5. Logging

### 5.1 Master experiment log

Append every experiment to `registry/EXPERIMENTS.md`. Do not delete old entries; append a correction or superseding entry.

Minimum columns:

```markdown
| ID | Status | Date | Owner | Stage | Parent | Eval version | Seeds | Main result | Resource result | Conclusion |
|---|---|---|---|---|---|---|---:|---|---|---|
```

Rules:

- Metrics come from `results.json`, not manual calculation.
- The conclusion is one evidence-based sentence.
- A failed or negative result explains why the idea should stop, change, or be revisited.
- Results using different split or evaluation versions are not placed on the same leaderboard without explicit reconciliation.
- Student experiments report relevant resource measurements together with predictive performance.

### 5.2 Decision log

Use `registry/DECISIONS.md` for shared decisions, including:

- experiment priorities and ownership;
- data, label, split, preprocessing, or evaluation changes;
- teacher freeze and student/runtime selection;
- acceptance thresholds and tie-break rules;
- use of unlabeled data or embeddings;
- stage transitions, releases, and reversals.

Each decision records the date, owner, alternatives, evidence, selected option, consequences, and condition for revisiting it.

### 5.3 Test and release logs

- Record every locked-test evaluation in `registry/TEST_ACCESS.md`.
- Record every frozen teacher, student candidate, mobile build, and final release in `registry/RELEASES.md`.
- Never overwrite a released model or its manifest. Create a new version.

## 6. Reporting

### 6.1 Personal status report

Each `researchers/rXX/STATUS.md` should remain short:

```markdown
# rXX Status

**Updated:** YYYY-MM-DD
**Current focus:**

## What I learned
- Evidence-based conclusions, not an activity list.

## Recent experiments
| ID | Result | Verdict |
|---|---|---|

## Related team work
- Work reused, reproduced, contradicted, or coordinated.

## Blockers and risks
- Items that require help or a shared decision.

## Next proposed work
- Experiment IDs or questions for team discussion.
```

### 6.2 Weekly team report

The rotating report owner writes `reports/weekly/<ISO-week>.md` containing:

- the most important finding of the week;
- current comparable leaderboard;
- short update for each researcher;
- confirmed improvements and dead ends;
- conflicting results requiring reproduction;
- duplicated or overlapping planned work;
- data, evaluation, compute, privacy, and device blockers;
- decisions made and decisions still needed; and
- agreed work for the next week.

The weekly meeting should discuss decisions, contradictions, and blockers. Researchers should read the written status before the meeting instead of presenting routine activity updates.

### 6.3 Stage reports

At the end of each stage, report:

- selected model or release and its versions;
- data and evaluation versions;
- overall, per-class, and relevant robustness results;
- repeated-run uncertainty;
- major ablations and negative findings;
- known limitations and remaining risks;
- artifact locations and hashes; and
- approval and handoff status.

Stage 2 additionally reports package size, peak RAM, latency, endurance, energy/thermal observations, mobile parity, and edge-only versus hybrid performance.

## 7. Minimum Team Rhythm

| When | Required action |
|---|---|
| Before a substantial experiment | Discuss priority, check prior work, and register the run |
| After any run | Validate, log, and write the conclusion |
| Twice per week | Update personal `STATUS.md` |
| Weekly | Review evidence, decide next work, and publish one team report |
| Before shared integration | Obtain review and confirm reproducibility |
| At a stage gate | Complete the detailed handbook checklist and release manifest |

## 8. Quick Checklist

Before starting work:

- [ ] I know my researcher ID and current agreed focus.
- [ ] I read the recent experiment and decision logs.
- [ ] My planned work is not an accidental duplicate.
- [ ] I created an experiment ID and folder.
- [ ] I recorded the question, parent, comparison, and decision evidence.
- [ ] I am using the official data, split, preprocessing, and evaluation versions.

Before declaring work complete:

- [ ] The shared evaluator produced `results.json`.
- [ ] Code, config, seed, environment, and artifacts are identifiable.
- [ ] I logged successful, negative, or failed outcomes.
- [ ] I wrote a clear conclusion and updated my status.
- [ ] Reusable changes were reviewed before entering shared directories.
- [ ] No raw audio, personal data, secret, or large unmanaged artifact was committed.

The team decides the research methods together. These guidelines make sure that, once a method is chosen, the work remains organized, comparable, reproducible, and visible to everyone.
